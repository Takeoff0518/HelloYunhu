### 实测记录

用示例配置里的占位令牌跑过一次自检，得到两条对真实服务端的观测：

- `GET /bot/info` 返回 `{"code":1003,"msg":"非法token"}`，说明响应外壳使用 `code` 与 `msg`，没有 `message`；
- 订阅端点对非法令牌返回 HTTP 401，说明该端点存在并且会校验令牌。

用真实令牌跑自检时发现成功响应的 `code` 为 1，`msg` 为 `success`，`data` 含 `botId`、`nickname` 等字段，订阅连接握手成功。代码原先只把 0 当成功，已改为同时接受 0 与 1。

第一次收发测试时事件全部被跳过，原因是 `sender.senderUserLevel` 实测是 `"owner"` 这类字符串，而结构体声明为整数；同一份事件还显示 `instructionId` 与 `commandId` 位于 `message` 内且为数字。两处类型已修正，并新增按真实事件构造的回归测试。群聊文本与图片的事件结构也与预期一致。

修正后群聊文本闭环打通：群里发消息，框架收到事件并回复，云湖群里能看到回复。发送接口的返回结构是 `{"messageInfo":{"msgId":"…"}}`，消息标识嵌在 `messageInfo` 里，原先按顶层 `msgId` 解析所以取不到，已改为优先读这个位置。引用与撤回现在有标识可用。

第二轮测试又确认两件事：图片 CDN 校验来源，不带来源头返回 403，附带 `Referer: https://myapp.jwznb.com` 后可下载，代码已对云湖域名自动附带；`/quote` 的引用关系没有生效，需要看发送请求里的 `parentId` 是否带上、平台是否采纳。为此增加了日志文件配置、发送请求明细与接口调用记录，下一轮据此定位。

第三轮测试的日志显示：图片下载成功，不再出现 403 告警；三条 `/quote` 都没有产生引用，原因是当时运行的测试机器人仍是旧进程，`/quote` 插件没有加载，全部落到回声插件，`parent_id` 均为空。同时确认了指令事件的结构：`instructionName` 与 `commandName` 是 `/quote`，正文只有参数，转换层原先把它当普通消息，指令名丢失。已改为把指令名拼回正文，并在扩展字段保留指令名。

第四轮测试中 `/quote` 命中了插件，但发送失败并返回 100：NoneBot2 把引用段的 `id` 序列化为字符串，而结构体声明为整数。已改为数字与字符串都能解析，`get_msg` 的 `message_id` 同样处理。

第五轮测试改用测试机器人主动调接口，不再依赖真人发消息。新增 `tools/testbot/plugins/m2accept.py`，`/m2check` 触发或按环境变量自动执行，依次核对机器人信息、群列表、群信息、群成员列表与成员信息、文本、图文混排、@、图片、文件、视频、私聊与本地状态。结果写入 `.m2check/result.json`。

这一轮得到四个结论：

- **群列表与群信息的群名一直是空的**，原因是平台返回的字段是 `name`，原实现按 `groupName` 解析。两个结构体已改为自定义解析，同时接受两种写法。
- **群成员接口需要授权**，未授权时返回 `1003` 与“机器人无获取群成员列表权限”，列表为空属于降级后的正常表现，不是解析错误。
- **图文混排按预期拆成三条**：日志里依次出现 `text`、`image`、`text` 三段发送，图片先上传拿到 `imageKey`，三条按顺序发出。这一项与发送 @、图片、文件、视频、私聊一起通过。
- **框架用 `file:///E:/…` 形式给出本地路径**，原实现只去掉 `file://`，留下 `/E:/…`，Windows 上读取失败。已按盘符去掉多余的前导斜杠。

重启验证也通过：第一轮记下整数标识，重启进程后用它作引用目标，日志里的 `parentId` 是重启前落盘的消息标识，说明映射表在重启后仍然可用。

这一轮还顺带验证了框架连接的重连：停掉测试机器人后连接被拒，退避间隔按 1、2、4、8、16、30 秒增长，框架重新监听后自动恢复，从断开到重连约 30 秒。云湖订阅侧的断线重连仍未实测。

第六轮测试由人工在群里操作，确认发送方向与唤醒链路，同时暴露两个与 @ 有关的问题：

- **正文里的昵称决定了提及怎么显示**。对照实验发了三条：正文写 `@昵称` 加空格时客户端显示为正常提及；只给 `at` 数组、正文不写时不显示提及；昵称后面只跟零宽空格时昵称与后文粘在一起。代码已改为用昵称缓存替换正文里的标识，取不到昵称时才写标识。
- **接收方向的提及文字没有剪掉**，框架收到的正文是「@乐正绫TwinkLing 零宽空格 `/diag`」，命令匹配不到，@机器人 发命令会落到回声插件。现在按 `at` 数组把正文里对应的「@昵称」剪掉，换成同一位置的 `at` 段。
- 昵称缓存取自消息事件里的发送者昵称，以及别人 @ 某人时正文里的名字，只存在内存里。进程刚启动时缓存为空，第一条 @ 可能仍显示标识。
- 诊断命令 `segments` 只显示 `text` 属正常现象：NoneBot2 会把开头指向自己的 `at` 段消费掉用于判断被 @，命令能命中正说明这条链路是对的。

群里发文件后的事件结构也顺手确认了：`content` 含 `fileName`、`fileUrl`、`etag`、`fileSize`。

第七轮测试补齐接收方向的媒体，并确认了撤回的行为：

| 媒体 | 事件字段 | 实际地址 | 结果 |
|---|---|---|---|
| 文件 | `fileUrl`：`c839….txt` | `https://chat-file.jwznb.com/…` | 200，转 base64 成功 |
| 视频 | `videoUrl`：`845f….mp4` | `https://chat-video1.jwznb.com/…` | 200，10.6 MB，转 base64 成功 |
| 语音 | `audioUrl`：`1ef1….wav` | `https://chat-audio1.jwznb.com/…` | 200，类型 `audio/x-wav`，转 base64 成功 |

三类地址都是相对路径，都要拼到各自的 CDN 上，并且都要求 `Referer: https://myapp.jwznb.com`，缺少时返回 403。视频这条是用户反馈后确认的：直接访问浏览器报 403，带上来源头返回 200。

撤回方面，`POST /bot/recall` 传 `msgId`、`chatId`、`chatType` 返回 `{"code":1,"msg":"success"}`，机器人自己的消息与他人消息都能撤回；但撤回之后订阅通道没有任何事件，说明平台不推送撤回通知，框架侧做不出 `notice.message_recall`。

`GET /bot/messages` 试过三种参数组合，只有 `chat-id` 加 `chat-type=group` 返回成功，内容为空列表，`chat-type=bot` 被拒绝，参数语义仍未摸清，暂时不用。

### 接口补齐

- `get_friend_list`：云湖没有机器人用户列表接口，官方 API 列表里的「获取机器人用户列表」标注为待上线，因此返回空数组。框架遍历空列表不会出错，比返回 1404 更安全，也不会拿虚构用户污染会话列表。单元测试断言响应是 `[]` 而不是 `null`。
- `tools/testbot/plugins/diagnostics.py` 新增 `/friends` 命令，用于在真实环境确认这个接口不报错。

### 能力声明接口

- `can_send_image` 与 `can_send_record`：按 OneBot 的规定回答框架的能力查询。前者默认真，后者默认假，因为云湖没有语音发送接口，语音只能按文件上传。
- 配置新增顶层 `capabilities` 段，两项都可覆盖。布尔值的零值与未配置无法区分，因此用指针解码，只覆盖写出来的字段。
- `can_send_record` 改成真不影响实际行为，只影响框架的判断，启动时打印一条提示说明这一点。示例配置里的注释写明了「客户端收到的仍是文件，不会出现语音气泡」。

### 调用后缀

- 分发前剥掉 `_async` 与 `_rate_limited` 后缀，两种写法和直接调用走同一个实现，响应状态为 `ok`。
- 没有异步队列，也没有限速排队。后缀只改变调用方是否等待，不改变执行方式，这个取舍写在支持矩阵的接口一节。
- 未实现的接口带后缀时，错误措辞保留调用方写的原始名字，便于对照日志。

### 日志文件

- 日志始终写入工作目录下的 `logs/`，文件名是当天日期，跨天后第一次写入时切换文件，后台把前一天的文件压缩成 `.gz`，并按保留天数删除过期文件。终端与文件内容一致。
- 配置去掉 `log.file`，新增 `log.keep_days`（默认 30，-1 表示永不删除，0 被拒绝）与 `log.compress`（默认开启）。
- 实现在 `internal/logging/rotate.go`，时钟作为字段注入，测试用假时钟模拟跨天与过期清理。Windows 上删除文件前必须先关闭句柄，实现里按这个顺序处理。
- 竞态修复：整理任务改为执行时读取当前日期，只处理日期早于今天的文件，并且同一时刻只允许一次整理。此前启动时的整理带着启动当天的日期去压缩，跨天后会把刚写出的新文件当成旧文件压掉，持续集成因此偶发失败。测试里的假时钟也加了锁。
- 文档同步：示例配置、测试指南第 1 节与第 7 节、架构说明新增第 10 节。

### 合并转发降级

- `internal/bridge/message/forward.go`：把节点树展开成文本，嵌套内容缩进一层，节点写成「昵称: 正文」，图片、文件、语音用占位文字。
- 每段 2000 字符，按节点边界断开，单个超长节点硬切；多段时每段开头加「[合并转发 i/n]」。嵌套超过 8 层、节点超过 500 个时截断并注明。
- 只带标识的转发展开成一行「[空的合并转发]」。
- `internal/bridge/message/message.go`：连续的转发节点合并展开，文本与转发按原顺序拆分成多条消息。
- `internal/onebot/action`：注册 `send_group_forward_msg`、`send_private_forward_msg`、`send_forward_msg`，参数里的节点数组走同一套展开逻辑。
- 测试机器人新增 `/forward`，发一条两层嵌套的转发用于真机确认排版。
- 文档同步：支持矩阵的消息类型表与接口表、协议映射第 2 节、README 概览、测试指南未涉及的细节写进支持矩阵。

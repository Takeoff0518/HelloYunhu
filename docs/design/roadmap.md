# 开发计划

本文档说明 HelloYunhu 的目标、范围、设计取舍、仓库结构、里程碑与工程规范。文档会随实现推进更新，但结构性调整需要先在本文档中记录理由。

## 1. 项目目标

HelloYunhu 在云湖机器人开放平台与 OneBot v11 协议之间做双向转换，使基于 OneBot v11 编写的机器人框架可以直接连接云湖。

首个正式版本以 AstrBot 的 aiocqhttp 适配器为主要验收对象。选择它作为基准，是因为 AstrBot 的用户规模最大，而且 aiocqhttp 对协议字段的要求比较严格，能满足它的实现通常也能满足 NoneBot2 与 Koishi。其他框架的兼容性在协议层保证，但不作为首个版本的验收条件。

## 2. 首个版本的范围

### 2.1 包含

- 事件：普通消息、指令消息、用户关注与取关、用户加入群与退出群。
- 接口：发送消息（M1 先实现群聊，M2 补齐私聊）、撤回消息、获取消息、获取机器人信息、获取群信息、获取群列表、获取群成员信息、获取群成员列表、获取陌生人信息、获取好友列表（平台暂无接口，返回空数组）、禁言、踢人、获取图片，以及 aiocqhttp 内部使用的快速操作接口与能力查询接口（`can_send_image`、`can_send_record`）。
- 消息段：文本、图片、@、引用、Markdown、文件、视频；语音与表情在没有对应能力时降级为文本提示。
- 连接方式：反向 WebSocket，角色为 Universal；一个机器人可同时接入多个框架连接。
- 运行方式：单进程服务一个云湖机器人；多个机器人开多个进程。

### 2.2 不包含

- 正向 WebSocket 与 HTTP 上报方式。
- OneBot 12 协议。
- 云湖用户账号协议。该协议需要登录真实用户账号，属于对客户端接口的逆向使用，不在本项目范围内。
- 合并转发的完整实现。首个版本只做文本降级。
- Web 管理界面。首个版本提供只读的诊断接口，界面放到正式发布之后。
- Docker 镜像。首个版本只提供三平台发行包，镜像在发布之后补。

## 3. 设计决策

### 3.1 连接方向

两条连接都由 HelloYunhu 主动发起。

与机器人框架之间使用反向 WebSocket，由框架监听端口、程序主动连接。这是 aiocqhttp 的设计方式，也是 NapCat、Lagrange 与 AstrBot 配合时的默认方式，用户不需要额外理解新的部署模型。

与云湖之间同样由程序主动连接订阅端点，而不是等待平台回调。这样部署时不需要公网地址，也不必处理回调地址的鉴权问题。

### 3.2 事件接收

首个版本默认使用 WebSocket 订阅接收事件。该端点没有出现在云湖官方文档中，但被多个社区适配器长期使用。因为存在变更的可能，代码中把地址做成可配置项，并在启动时做一次连通性检查，失败时给出明确提示。

Webhook 接收方式已经实现，需要平台能访问到监听端口，路径里带令牌。两种方式同时启用时，以事件标识去重，保证同一条消息只处理一次；去重表在内存里保留十分钟。

### 3.3 一个进程一个机器人

一个进程服务一个云湖机器人，可以同时挂多个到框架的连接，事件转换一次后广播给所有连接。这样同一个云湖机器人可以同时接入 AstrBot 与 NoneBot2，各自处理自己关心的消息。

多个机器人不再由单进程承载，直接多开进程，每个进程一份配置。这样做是因为单进程多实例在实际使用中几乎不出现，而多框架接入是常见需求；按进程隔离以后，配置、日志与故障域都更清楚。

### 3.4 身份标识

云湖的用户、群与消息标识都是字符串，其中消息标识是 32 位十六进制；OneBot v11 与 AstrBot 的若干代码路径要求整数。

程序在内部维护一张映射表，把云湖标识映射为稳定的 64 位整数，对外只暴露整数。消息标识单独一张表，并设置过期时间，因为它的数量增长远快于用户与群。原始标识放在事件的扩展字段中，便于排查问题。

映射表持久化保存，程序重启后仍然有效，否则用户重启后旧消息的引用与撤回会失效。

### 3.5 消息发送

OneBot 的一条消息可以包含多种消息段，例如文本、图片与 @ 混排；云湖的一条消息只能有一个内容类型。

发送时按顺序把消息段拆成若干条云湖消息：连续的文本与 @ 合并为一条，图片、文件、视频各自单独一条。图片与文件必须先上传取得标识，不能直接传网络地址。任何一段上传失败时，用文本说明替代，保证用户至少能看到提示，而不是消息静默丢失。

发送类接口不自动重试。机器人重复发言的代价远高于一次发送失败，失败信息交给日志和接口返回值。

### 3.6 存储

使用 SQLite，通过纯 Go 驱动访问，不依赖 cgo，方便交叉编译出各平台的可执行文件。存储只保存映射关系与去重记录，不保存消息正文，避免引入隐私问题。

### 3.7 接口返回

OneBot 接口统一返回状态、返回码、数据与回显字段。未实现的接口返回 1404 与文字说明，不返回成功。这一点在调研中反复确认过：框架对返回码的检查并不严格，但对状态字段与回显字段有硬性要求，任何一个缺失都会表现为超时或异常，而不是清晰的错误。

### 4.3 依赖规则

- `internal/onebot` 与 `internal/yunhu` 互不引用，两个平台包只认识自己的协议。
- `internal/bridge` 是唯一同时依赖两侧模型的层，所有语义转换集中在这里。
- `internal/app` 负责装配，其他包不反向依赖它。
- 任何包都不引用 `cmd`。
- 平台包不直接访问数据库，需要持久化时通过接口由上层注入。

这样划分的目的是让协议变化的影响范围可控：云湖接口调整只影响 `internal/yunhu` 与 `internal/bridge`，OneBot 侧的兼容性调整只影响 `internal/onebot` 与 `internal/bridge`。

## 6. 测试策略

单元测试覆盖转换逻辑，包括 CQ 码编解码、消息段与云湖消息的相互转换、事件映射与标识映射。测试采用表驱动写法，复杂的输入输出保存在 `testdata` 目录，作为基准文件比对。

集成测试使用 `httptest` 模拟云湖接口，使用本地 WebSocket 服务模拟机器人框架，验证一次完整的接收与发送流程，重点检查协议字段是否齐全、回显是否正确。

端到端测试使用真实的云湖测试机器人与机器人框架，按照检查清单人工验证，清单保存在 `docs/guides/testing.md`。这部分不放进持续集成，因为需要真实账号。

端到端测试所用的机器人框架放在 `tools/testbot/`，是一个基于 NoneBot2 的最小实现，提供回声与诊断命令。它属于测试资产，不参与主程序构建，也不引入 Go 依赖；后续新增测试场景时在它的 `plugins/` 下扩展。最终验收仍以 AstrBot 为准，`tools/testbot` 只用于快速验证协议链路。

涉及并发的代码使用竞态检测运行测试。转换与映射相关包的覆盖率目标为七成，其余包不设硬性指标。

## 8. 工程规范

提交信息使用 Conventional Commits 格式，正文说明修改动机与影响范围。`main` 分支始终保持可构建、测试通过，功能在独立分支开发，通过 Pull Request 合并，即使单人开发也保留这个过程，便于回溯。

源文件首行添加 SPDX 许可证标识。错误使用 `%w` 包装，只在上层最终处理的位置记录一次日志。所有网络与数据库操作接受 `context.Context`。不使用全局可变状态，共享状态由所属结构体持有并加锁，或者在单个协程内访问。

配置在启动时完整校验，非法配置直接退出并说明具体原因，不做静默降级。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 订阅端点属于未公开接口，可能变更或关闭 | 核心链路中断 | 地址可配置，启动自检，保留 Webhook 作为备用方式 |
| Webhook 没有签名机制，事件可能被伪造 | 消息注入 | 在路径中加入随机密钥，限制来源地址，按事件 ID 去重 |
| 云湖接口仍在演进，字段可能调整 | 解析失败 | 解析保持宽松，未知内容降级处理，接口变更时快速发版 |
| AstrBot 升级可能改变适配器行为 | 兼容性回退 | 固定版本做回归测试，在文档中记录已验证版本 |
| 映射表损坏或丢失 | 引用与撤回失效 | 定期备份，提供重建命令，映射丢失时返回明确错误 |
| 图片与语音以 base64 传输，单条消息体积大 | 连接被关闭 | 提高 WebSocket 消息大小上限，限制并发的大消息数量 |

# 架构说明

本文档说明 HelloYunhu 的模块划分、数据流、并发模型与错误处理。它对应 M1 完成时的实现，后续里程碑会补充媒体、持久化与限流部分。

## 1. 连接方式

程序只发起出站连接，不需要公网地址。一个进程服务一个云湖机器人，连接分两类：

| 连接 | 方向 | 作用 |
|---|---|---|
| 订阅连接 | 我们连 `wss://ws.jwzhd.com/subscribe` | 接收云湖推送的事件，默认方式 |
| Webhook | 云湖 POST 到我们监听的端口 | 可选的接收方式，需要公网可达 |
| 框架连接 | 我们连 `ws://框架地址/ws` | 向框架推送事件，接收框架发来的接口调用 |

框架连接可以有多个，每个对应一个框架，事件会广播给所有连接。所有连接握手时都用同一个 `X-Self-ID`，取自云湖 `/bot/info` 返回的 `botId`，因为云湖事件本身不含机器人标识；握手头固定为 `X-Self-ID`、`X-Client-Role: Universal` 与可选的 `Authorization: Bearer`。

## 2. 模块与依赖

```
cmd/helloyunhu          命令行入口，解析参数、创建上下文、调用 app
internal/app            装配：读取配置、创建日志、启动接收与框架连接
internal/config         配置结构、默认值、加载与校验
internal/logging        log/slog 初始化与按日切分的日志文件
internal/yunhu/model    云湖事件与接口的数据结构
internal/yunhu/api      云湖接口客户端
internal/yunhu/subscribe 订阅连接
internal/yunhu/webhook  HTTP Webhook 接收
internal/onebot/model   OneBot 事件、消息段与响应
internal/onebot/client  反向 WebSocket 连接、回显匹配
internal/onebot/action  接口调用实现
internal/bridge/identity 标识映射
internal/bridge/message 消息段与云湖消息的转换
internal/bridge/event   云湖事件到 OneBot 事件的转换
internal/bridge/dedup   两种接收方式同时启用时的事件去重
```

依赖方向是单向的：`cmd` 依赖 `app`，`app` 依赖其余所有包；`bridge` 同时依赖两侧的模型，两侧的模型互不依赖；`yunhu` 与 `onebot` 之间没有直接依赖。这样云湖侧调整只影响 `yunhu` 与 `bridge`，OneBot 侧兼容性调整只影响 `onebot` 与 `bridge`。

## 3. 数据流

**接收方向。** 订阅连接读到一帧，或 Webhook 收到一次 POST，解析成事件外壳后写入事件通道。两种方式同时启用时先按 `eventId` 去重，重复的只保留第一条。转发协程取出外壳，按事件类型解析负载，换算标识，构造 OneBot 事件，广播给所有框架连接。事件通道容量为 64：订阅侧写满时读循环等待，背压传导到网络层；Webhook 侧写满时返回 503，让平台稍后重试，不挂住请求。

**发送方向。** 框架写入一帧接口调用，连接层按 `action` 与 `params` 解析，交给接口处理器。处理器把消息段整理成云湖文本消息，调用 `/bot/send`，把返回的消息标识登记到映射表，最后按 OneBot 格式写回响应。响应必须带回框架给出的 `echo` 原对象，否则框架会等到超时。

**连接建立。** 框架连接握手成功后，立即发送 `meta_event.lifecycle.connect` 事件，框架据此打印「已连接」并开始工作。

## 4. 并发模型

每个进程常驻的协程：

| 协程 | 职责 |
|---|---|
| 订阅连接 | 读事件、重连、写入内部通道（仅 websocket 或 both 模式） |
| 订阅事件投递 | 去重后写入事件通道，保持背压 |
| Webhook 接收 | HTTP 服务，校验令牌与来源，去重后投递（仅 webhook 或 both 模式） |
| 框架连接 | 每条连接一个协程：读接口调用、写事件与响应、重连 |
| 事件转发 | 转换事件、广播给所有框架连接 |

每个接口调用额外启动一个协程，避免一次慢调用阻塞读循环。框架连接上的写入由互斥锁保护，并设置 10 秒写超时；读取上限放大到 64 MB，因为框架会把图片与语音整段内联成 base64。

上下文取消时，所有连接都会主动关闭自身，读循环不会阻塞到对端断开。单个框架连接断开只重连，不影响进程；订阅连接与机器人信息查询失败属于致命错误。

## 5. 错误处理与重试

| 场景 | 处理 |
|---|---|
| 订阅连接或框架连接断开 | 按 1 秒到 30 秒的指数退避重连，连接成功建立过后重置间隔 |
| 发送消息失败 | 不重试，错误如实返回给框架，并记录日志 |
| 云湖返回业务错误码 | `*APIError` 包装错误码，`1007` 表示触发频率限制，可用 `errors.Is(err, api.ErrRateLimited)` 判断 |
| 调用频率 | 客户端按 `yunhu.rate_limit` 匀速放行，默认每秒十次，等待受上下文控制；超限错误不自动重试 |
| 接口未实现 | 返回 `retcode=1404` 与说明，不返回成功 |
| 参数不合法 | 返回 `retcode=100` 与说明 |
| 其它内部错误 | 返回 `retcode=1500`，说明写进 `wording` |
| 事件解析失败 | 记录日志并跳过这一条，不中断连接 |
| 暂不支持的消息内容 | 转为占位文本，用户至少能看到提示 |

发送路径不自动重试是有意为之：机器人重复发言的代价高于一次发送失败，失败信息交给日志与接口返回值。

## 6. 标识映射

云湖的用户、群与消息标识都是字符串，其中消息标识是 32 位十六进制；OneBot 的多处代码要求整数。

用户与群标识是十进制数字，直接解析即可。消息标识需要一张表：接收消息时分配递增整数，发送引用时反查回原始标识。

映射表存放在 SQLite 中，使用纯 Go 驱动，不依赖 cgo。云湖的消息标识唯一，整数由自增主键分配，重启后再查同一个标识会拿到同一个整数。同一张表还保存消息所属的会话标识与会话类型，撤回因此不会因为重启而失效。写入采用先查后插：命中时不写库，避免自增序列被无效写入消耗；插入使用 `DO NOTHING`，并发写入时重新查询取得已分配的整数。连接池限制为单连接，并发调用排队而不是遇到锁冲突。旧库缺少会话两列时，启动阶段按列名检查并用 `ALTER TABLE` 补上。

映射表按保留时长清理，启动时先清理一次，之后每小时一次。消息标识的增长速度远快于用户与群，不清理会无限膨胀。

解析失败时退化为稳定哈希，并在转换层记录一次日志。这样标识仍然可比较，但已经失去可读性，属于需要关注的异常。

## 7. 当前限制

- 消息内容覆盖文本、图片、文件、视频与语音。语音接收为 `record` 段，发送按文件消息处理，因为云湖没有语音发送能力。
- 图片、文件、视频与语音在接收方向都先下载再以 base64 交给框架，体积上限由媒体读取器控制；下载失败时退化为直接给出地址。四类媒体的 CDN 地址规则见 [协议映射说明](protocol-mapping.md) 第 3 节。
- @ 段按正文里的提及位置切分，正文里没有对应的 `at` 时保留原文。
- 撤回依赖标识映射表里的会话信息，重启后仍可撤回旧消息；平台不推送撤回通知。
- 通知类事件（关注、入群、退群）尚未转换，收到时记录日志并跳过。
- 心跳事件尚未发送。首个验收框架不依赖它，其它框架在后续补齐。
- 群成员接口需要机器人在群后台获得权限，未授权时降级为空数据，保住 @ 唤醒。

## 8. 只读诊断接口

配置 `diagnostics.enabled` 为真时，进程在 `diagnostics.listen` 上启动一个只读 HTTP 服务，提供两个端点：

| 端点 | 内容 |
|---|---|
| `GET /healthz` | 返回 `ok`，用于探活 |
| `GET /status` | 返回 JSON：版本、启动时间、运行秒数、实例数量、已处理事件数与调用数 |

服务只读，写请求返回 405，不输出消息正文、令牌与用户标识。默认关闭，开启后建议只监听回环地址。

## 9. 自检与调试

`selftest` 子命令做真实检查：查询机器人信息、握手订阅端点（使用中时）、逐个握手框架端点。检查只建立连接后立即关闭，不进入消息循环，因此可以在正式启动前反复执行，也不会让框架登记成可用连接。Webhook 接收无法由自检代替，列为跳过项。任一检查失败时退出码为 1。

排查协议问题时把日志级别设为 `debug`，并打开 `log.raw_events`。该开关输出订阅收到的原始事件帧，长度截断到 4 KB；关闭时只记录事件类型与解析错误。接口返回非零错误码或响应无法解析时，错误信息会带上响应原文片段，避免为了确认字段名再加临时打印。

## 10. 日志文件

日志始终写入当前工作目录下的 `logs`，同时输出到终端。文件名是当天日期，例如 `2026-11-15.log`，跨天后第一次写入时切换到新文件，不需要定时器。

写入前比较当天日期与当前打开的文件日期，不同就关闭旧文件、打开新文件，并在后台启动一次整理：把前一天的文件压缩成 `2026-11-15.log.gz`，删除超出保留天数的文件。压缩与删除在独立协程里完成，不阻塞写日志；进程退出时等待这些任务结束再关闭文件。

保留天数由 `log.keep_days` 决定，默认 30 天，-1 表示永不删除，0 不被接受。压缩由 `log.compress` 控制，默认开启。整理失败只写一条提示，不影响日志继续写入。

## 11. Webhook 接收

`receive.mode` 为 `webhook` 或 `both` 时，进程在 `receive.webhook.listen` 上启动一个 HTTP 服务，只接受 `POST /yunhu/<token>`。

云湖的 Webhook 没有签名，路径里的令牌是唯一凭据，因此校验是三条一起做：

| 措施 | 行为 |
|---|---|
| 路径令牌 | 与配置里的令牌做常量时间比较，不匹配返回 404，与路径不存在不作区分 |
| 来源网段 | `allowed_ips` 非空时只接受这些网段，其余返回 403；为空表示不限制 |
| 请求体上限 | 默认 1 MiB，超限返回 413，避免用超大请求体消耗内存 |

请求体按事件外壳解析，缺少 `header.eventType` 返回 400。通过校验后交给投递函数写入事件通道；通道满时返回 503，让平台稍后重试。请求体不写日志，也不回显。

`both` 模式下两种来源共用一张去重表：按 `eventId` 记录，10 分钟过期，容量 4096，进程重启后清空。重启窗口内平台重试的事件可能重复转发一次，这一点写在支持矩阵里。

这套切分依赖单进程独占日志目录。多个实例在一个进程里由同一个写者输出，没有问题；多个进程写同一个目录会互相覆盖，属于不支持的使用方式。解释器的时区取进程所在环境的本地时区，跨时区变更需要重启进程。

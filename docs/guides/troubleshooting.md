# 常见问题

本文按故障出现的阶段组织：启动、与框架的连接、事件接收、消息发送、媒体与显示，最后是日志与诊断。每条先给出日志原文，再说明原因与处理步骤。日志同时输出到终端与 `logs/` 下当天日期的文件，下面引用的内容可以直接在文件里搜索。

首次接入的步骤见[快速开始](quickstart.md)，字段含义见[配置说明](configuration.md)，各项能力的状态见[功能支持情况](compatibility.md)。

## 1. 启动阶段

### 第一次运行只生成配置就退出

```
已生成配置文件 config.yaml，本次不启动。
请填写以下两项后再次运行：
  bot.token          云湖机器人令牌
  onebot[0].url      机器人框架的 WebSocket 地址
```

这是首次运行的正常行为：程序发现配置文件不存在，写出一份模板之后退出，退出码为 0。填好这两项再运行即可。

### 配置校验未通过

```
配置校验未通过:
bot.token: 不能为空
```

进程在建立任何连接之前退出，说明配置文件里至少有一项取值不合法。校验会把所有问题一次列出，逐条对照[配置说明](configuration.md)第 11 节的表修改，全部通过之后进程才会启动。

### 字段名拼错或者沿用旧版结构

```
解析配置文件 config.yaml: YAML 格式错误: yaml: unmarshal errors:
  line 1: field instances not found in type config.Config
```

程序拒绝未知字段。旧版的多实例配置使用 `instances`，当前版本改成 `bot`、`receive` 与 `onebot` 三段，旧配置需要按[配置说明](configuration.md)重写。

### 端口已被占用

Webhook 监听端口被占用时，进程启动后立即退出。Windows 上的报错如下，Linux 上的提示是 `address already in use`：

```
level=ERROR msg=组件异常退出 component="Webhook 接收" err="listen tcp 0.0.0.0:8081: bind: Only one usage of each socket address is normally permitted."
```

先确认没有第二个 HelloYunhu 进程使用同一个端口，再检查 `receive.webhook.listen` 与系统上其他服务的端口分配。诊断接口的端口被占用只影响诊断接口本身，进程继续运行，日志里记录一条「诊断服务退出」。

### 日志目录或数据库无法创建

进程启动即退出，错误信息里包含具体路径。工作目录没有写权限、磁盘已满、或者 `storage.path` 指向一个不存在的分区时会触发。把可执行文件放在可写目录里，或者把 `storage.path` 指向一个已存在且可写的目录。

## 2. 与框架的连接

### 启动后持续输出「框架连接中断，准备重连」

```
level=WARN msg=框架连接中断，准备重连 err="dial tcp 127.0.0.1:8080: connectex: No connection could be made because the target machine actively refused it." retry_in=1s
```

重试间隔从 1 秒开始按 2 倍增长，上限 30 秒。出现这一行有两个常见原因：框架进程尚未启动，或者它监听的端口与配置里的 `onebot[].url` 不一致。

1. 确认框架进程正在运行，记录它打印的监听地址。
2. 核对 `onebot[].url` 的协议、主机、端口与路径。路径由框架决定，`/ws` 与 `/onebot/v11/ws` 属于常见写法，具体取值以框架启动日志为准。
3. 修改配置后重启 HelloYunhu，框架进程保持运行。

这一行是重试提示。框架开始监听后，日志会输出「已连接机器人框架」，并附带框架报告的机器人标识。

### 自检里框架握手返回状态码 400

```
[失败] 框架握手 astrbot: 握手失败，状态码 400: websocket: bad handshake
```

框架拒绝握手。常见原因是 `onebot[].url` 填成了普通 HTTP 地址，或者填的是框架的管理页面路径，而不是反向 WebSocket 端点。按框架文档确认端点路径，NoneBot2 的 adapter-onebot 默认是 `/onebot/v11/ws`，AstrBot 的 aiocqhttp 适配器默认是 `/ws`。

框架开启访问令牌时，握手会带上 `Authorization: Bearer <access_token>`，两侧的令牌必须一致，否则同样表现为握手失败。

### 日志出现「框架连接尚未建立，事件已丢弃」

```
level=WARN msg=框架连接尚未建立，事件已丢弃 event_id=…
```

框架断开期间云湖推送了事件。程序按设计丢弃这条事件，等连接恢复后继续转发后续事件；这条消息已经丢失，需要用户重新发送。

降低影响的办法是让框架先启动、HelloYunhu 后启动，并在日常维护时先停 HelloYunhu、再停框架。

### 接口调用失败

框架调用接口但执行失败时，日志有两种形式。

内部的网络或解析错误：

```
level=ERROR msg=接口调用失败 action=send_group_msg err=…
```

业务错误，返回码来自 OneBot 协议：

```
level=INFO msg=接口调用未成功 action=delete_msg retcode=1404 wording="消息 12345 没有对应的云湖标识"
```

`retcode` 的 1404 表示接口或数据不存在，100 表示参数不合法，1500 表示上游实现出错。处理方式取决于 `action`：先对照[功能支持情况](compatibility.md)第 4 节确认该接口是否可用，再按 `wording` 里的说明检查参数。

### 框架里显示的产品名是 gensokyo

`get_version_info` 返回的 `app_name` 默认为 `HelloYunhu`。如果框架的日志、`/overflow` 这类状态命令显示的是 `gensokyo`，说明配置里开启了 `compat.gensokyo.enabled`。

这不是接错了客户端，也不是程序改名。兼容模式为了让只认这个名字的客户端启用头像扩展，会主动自报该名字，详见[配置说明](configuration.md)第 9 节。不需要云湖头像时把 `enabled` 改成 `false` 即可恢复。

## 3. 事件接收

### 启动时退出，报错误码 1003

```
错误: 获取机器人信息: 云湖接口 GET /bot/info 返回错误码 1003: 非法token（原始响应: {"code":1003,"msg":"非法token"}）
```

云湖拒绝了机器人令牌。到[云湖](https://www.yhchat.com/)机器人后台核对令牌，或者重置之后更新 `bot.token`。原始响应附在错误信息末尾，字段名与平台实际返回不一致时会一并显示，反馈问题时保留这一段。

### 订阅连接握手失败，状态码 401

```
level=WARN msg=订阅连接中断，准备重连 err="订阅握手失败，状态码 401: websocket: bad handshake" retry_in=1s
```

订阅端点拒绝了当前令牌，或者 `yunhu.subscribe_url` 已经失效。先确认令牌有效，再核对订阅地址。这个端点属于未公开接口，平台调整地址时需要修改配置。

### 群里发消息，框架收不到

按下面的顺序确认：

1. 机器人是否已经在群里。群消息由机器人账号接收，机器人入群之前收不到任何群事件。
2. 群里 @机器人 的消息是否被框架的命令匹配消费。NoneBot2 会消费开头的 `at` 段用于判断被 @，调试时看到 `segments` 里只有 `text` 属于正常现象。
3. 是否机器人自己发出的消息。程序按 `senderId` 过滤自身消息，debug 级别下记录「忽略机器人自己发出的消息」。
4. 事件类型是否已知。未知事件在 debug 级别记录「未知事件类型，已跳过」。
5. Webhook 模式下，云湖控制台的订阅地址是否指向 `http://<listen>/yunhu/<token>`，返回码见下一条。

### Webhook 推送的返回码对照

| 返回码 | 原因 | 处理 |
|---|---|---|
| 200 | 事件已接收 | 无需处理 |
| 405 | 请求方法不是 POST | 改由云湖推送，人工验证时使用 `curl -X POST` |
| 404 | 路径或者令牌不对 | 核对订阅地址里的 `<token>` 与配置一致 |
| 403 | 来源不在 `allowed_ips` 里 | 补上平台出口网段，或清空该列表 |
| 413 | 请求体超过 1 MiB | 事件体积异常，检查推送来源 |
| 503 | 事件通道已满 | 通常是某条框架连接写入阻塞，稍后由平台重试 |
| 400 | 请求体不是合法 JSON，或者缺少 `eventType` | 检查推送内容与来源 |

### 同一事件收到两次

`both` 模式下两种来源都会送达同一条事件，程序按 `eventId` 去重，debug 级别下记录「重复事件已过滤」。框架侧仍然收到两条，说明两条事件的标识不同，属于平台对同一条消息的两次推送；这时按事件内容判断，处理逻辑需要幂等。

### 日志出现「转换事件失败，已跳过」

```
level=WARN msg=转换事件失败，已跳过 event_type=message.receive.normal err=…
```

事件结构与预期不一致，转换层无法得到完整的消息段。把 `log.raw_events` 设为 `true` 后由平台重发同一条消息，对比原始事件与[协议映射说明](../design/protocol-mapping.md)第 2 节的字段记录。确认差异之后按实际结构修正解析，反馈问题时附上原始事件的片段。

## 4. 消息发送

### 接口返回 1404

1404 表示接口或数据不存在，常见于三种情况：

| 场景 | 原因 | 处理 |
|---|---|---|
| 调用了未实现的接口 | 平台没有对应能力，或者列入后续版本 | 对照[功能支持情况](compatibility.md)第 4 节 |
| `delete_msg` 或 `get_msg` 返回 1404 | 消息标识不在映射表里 | 检查 `storage.message_ttl`，映射过期后无法再操作 |
| 引用的消息被忽略 | 引用目标不在映射表里 | 日志记录「引用的消息不在映射表中，已忽略引用」，消息照常发出 |

### 接口返回 100

参数缺失或者取值不合法，`wording` 会指出具体字段，例如 `send_group_msg 缺少 group_id`。对照框架侧发起调用时传入的参数修改。

### 撤回、禁言、踢人返回 1003

机器人没有对应权限。到群后台为机器人开启管理权限，撤回他人消息与禁言都需要这个权限。

程序在失败后会再查一次群信息。如果能确认缺少的是哪一项权限，返回码改成 1500，`wording` 里直接写出开关名，例如「机器人在群 695367192 没有禁言权限，请在云湖群后台为机器人授予 allowGagMember」。按这句话到群后台开启对应开关即可。

### 群管插件提示权限不足，或者对命令没有反应

插件读的是机器人的角色，而云湖没有群主与管理员这类身份，机器人默认报 `member`。到群后台为机器人开启任意一项管理权限之后，`get_group_member_info` 返回的 `role` 变成 `admin`，不需要重启程序。

对应关系是禁言看 `allowGagMember`，踢人看 `allowRemoveMember`。开启其中任意一项就够，程序把四项写入权限里的任意一项换算成 `admin`。实际开关可以用 `get_group_info` 的 `yunhu_permissions` 查看，字段含义见[扩展字段](extensions.md)第 3 节。

开启之后仍然没有反应时，检查日志里有没有本程序返回的错误。角色只影响插件是否继续执行，不接受的操作仍由云湖拒绝。

### 接口返回 1007

云湖接口的频率超过每秒十次。多个进程共用同一个机器人令牌时，各自按 `yunhu.rate_limit` 限流，合计之后仍可能超过平台上限。处理办法是合并成一个进程，或者在每个进程里把 `yunhu.rate_limit` 降到十次除以进程数。

### 禁言时长与请求的不一致

平台只接受四个档位：600、3600、21600 与 43200 秒，另外 0 表示解禁，-1 表示永久。其它时长向上取到最近的档位，超过 43200 秒按 43200 秒处理，因此请求禁言一分钟实际生效十分钟。

### 发送图片时报「文件类型必须为图片」

```
level=ERROR msg=接口调用失败 onebot=… action=send_group_msg err="上传图片: 云湖接口 POST /image/upload 返回错误码 -1: 文件类型必须为图片（原始响应: {\"code\":-1,\"msg\":\"文件类型必须为图片\"}）"
```

云湖按上传表单里的文件名后缀判断类型，内容也必须是真正的图片。0.1.0 把 `base64://` 形式的内容统一命名为 `upload.bin`，后缀不是图片，一定得到这个错误，升级到 0.1.1 即可解决。0.1.1 起程序在上传前按内容探测补齐 `.png`、`.jpg` 这类后缀，视频同样补成 `.mp4`。

升级后仍然出现时，说明框架给出的内容本身不是图片。常见原因是框架传的是图片地址，而这个地址返回的是网页或占位图。让插件确认地址能直接下载成 PNG 或 JPEG，再重试。

### 一条消息在群里变成多条

云湖一条消息只有一个内容类型，而 OneBot 的一条消息可以包含多个消息段。程序按顺序拆分：连续的文本与 @ 合并成一条，图片、文件、视频各自一条，引用只挂在拆分后的第一条上。这个行为属于协议差异，无法合并成一条发送。

### 日志出现「云湖没有返回消息标识」

```
level=WARN msg=云湖没有返回消息标识，引用与撤回将不可用 recv_type=group recv_id=…
```

消息已经发出，但响应里没有 `messageInfo.msgId`，程序无法为它分配整数标识。这条消息后续不能引用与撤回。确认平台发送接口的响应结构是否调整过，原始响应在 debug 级别的「云湖接口返回」记录里。

## 5. 媒体与显示

### 图片、文件或视频在框架侧打不开

接收方向的媒体由程序下载后以 `base64://` 传给框架，单次读取上限 20 MB。超过上限时日志记录：

```
level=WARN msg=下载媒体失败，已退化为直接给出地址 kind=video err=…
```

这时框架收到的是云湖的原始地址，而云湖的媒体 CDN 校验来源，框架直接请求会得到 403。处理办法是让对方发送更小的文件；上限目前是代码里的常量，调整需要改代码。

### 头像显示成陌生人

头像不经过本程序，OneBot v11 的 `sender` 里没有头像字段。框架与插件通常把整数标识当作 QQ 号去 qlogo 取图，云湖的数字标识在 QQ 上大多对应真实存在但无关的账号，因此显示成陌生人的头像。

客户端是 Overflow 这类 mirai 客户端时，同时开启 `proxy.enabled` 与 `compat.gensokyo.enabled` 并重启，头像会换成云湖里的真实头像。程序会在 `/avatar/<标识>` 上提供代理，取图时自行附带来源头。头像地址表只记录见过的人，刚启动时群里还没人发过消息，显示的是灰色占位图，等对方发一条消息即可恢复。

AstrBot 与 NoneBot2 不调用 `get_avatar`，开启兼容模式对它们没有作用。

### 语音在客户端显示为文件

云湖没有语音发送接口，发送 `record` 段时按文件上传，客户端收到的是一个需要点开收听的音频文件。这是平台能力限制，见[功能支持情况](compatibility.md)第 5 节。

### @ 显示成数字标识

平台的正文里必须出现 `@昵称` 才会渲染成提及。昵称来自收到过的消息事件，进程刚启动、还没有收到过这个人的消息时，第一条 @ 会显示数字标识。等这个人再发一条消息，昵称进入缓存之后即可正常显示。

### 合并转发变成一段文字

云湖没有合并转发类型，`send_group_forward_msg` 一类接口会把节点树展开成文本，每条节点写成「昵称: 正文」，嵌套内容缩进一层，超过 2000 字符时按节点边界分段，每段开头带「[合并转发 i/n]」。展开后的内容无法还原成原始结构，这是当前版本的既定行为。

### Markdown 消息变成占位文字

收发两个方向都还没有 Markdown 的协议细节，接收时得到 `[暂不支持的消息类型: markdown]`，发送时同样降级为文本。平台有这个内容类型，后续版本再补。

## 6. 日志与诊断

### 打开详细日志

把 `log.level` 设为 `debug` 可以看到接口调用、消息发送与事件转换的细节。核对平台字段时再把 `log.raw_events` 设为 `true`，程序会输出收到的原始事件，每条截断到 4 KB：

```yaml
log:
  level: debug
  raw_events: true
```

原始事件包含消息正文、昵称与群标识，排查结束后改回 `false`。把日志发给他人之前，先删除令牌、群标识与昵称。

### 找到日志文件

日志写在启动目录下的 `logs/` 里，文件名是日期，例如 `2026-11-15.log`。跨天之后的第一次写入会切换到新文件，前一天的旧文件在后台压缩成 `.gz`，超过保留天数的文件在整理时删除。查看压缩日志用 `zcat 2026-11-14.log.gz`，Windows 上可以用 7-Zip 打开。

### 查看运行状态

把 `diagnostics.enabled` 设为 `true` 并重启，`GET /status` 返回当前状态：

```
curl http://127.0.0.1:9090/status
```

重点看两项：`bot_id` 在启动查询成功后才有值；`connections` 里每项的 `online` 为假表示当前没有建立连接。`events_received` 与 `actions_handled` 持续增长，说明事件与调用都在正常流转。

### 反馈问题时提供的内容

- `helloyunhu version` 的输出，包含版本、提交与 Go 版本。
- 启动时的完整日志，从「程序启动」到出错为止。
- 出错时间点前后各一段日志，文件路径与行号越具体越好。
- 云湖接口报错时，错误信息末尾的「原始响应」片段。

发送前删除令牌、群标识与用户昵称，这些内容在日志里都有出现。
